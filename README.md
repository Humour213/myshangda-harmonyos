# 我的商大 · HarmonyOS

浙江工商大学移动门户「我的商大」的 HarmonyOS ArkTS 社区适配版。项目使用原生 ArkUI 搭建底部导航与页面框架，通过 ArkWeb 承载学校官方 H5 业务，登录、数据与业务请求均直连学校官方系统。

> 本项目由社区爱好者开发，**并非学校官方应用**。应用内所有业务内容、商标与校园素材版权归浙江工商大学及相关权利方所有。

## 应用简介

「我的商大」是浙江工商大学的统一移动门户，提供校园码、教务查询、成绩查询、资讯、审批、通讯录等服务。本应用面向 HarmonyOS 设备，将官方移动门户的 H5 页面封装为原生体验：

- 使用原生底栏与标题栏，避免网页嵌套带来的割裂感；
- 复用学校统一身份认证，不搭建任何中间服务器；
- 针对 zfsoft 门户与通讯录 H5 补充 Android 桥兼容层，使二级页面、分享、版本检测等功能在 HarmonyOS 上可用；
- 在网络不稳定时优先展示本地缓存，并在网络恢复后自动重连。

## 应用特色

### 原生外壳，网页内核

- 底部导航：消息、审批、主页、通讯录、我的，对应门户的五个主入口。
- 首页、审批、消息、我的提供原生骨架，业务列表仍由官方 H5 渲染，保证信息与学校系统实时一致。
- 子页面使用 `NavDestination` 独立承载，支持标题栏、返回手势与深链打开。

### 双外观样式

设置中可切换「鸿蒙原生」与「经典」两套外壳：

- **鸿蒙原生**：使用 `HdsTabs` / `HdsNavigation`，配合系统材质与悬浮底栏，状态栏与底部小白条沉浸显示。
- **经典**：保留原版 App 的顶部渐变标题栏与方形图标风格。

切换后主页、子页面、设置页会同步应用对应外壳。

### 快速登录与自动登录

- 首次启动直接使用原生登录页，校验通过后再进入门户，避免网页登录页反复跳转。
- 支持「记住密码」，凭据保存在应用私有 Preferences 中，仅用于向学校统一身份认证提交。
- 门户 H5 需要登录态时，注入脚本会等待 RSA 公钥就绪并检测验证码状态，满足条件后自动提交，否则回退到网页登录页。
- 设置页提供「退出登录」，可清除本地保存的凭据与网页数据。

### 离线优先与自动重连

- 启动与切换 Tab 时先探测网络，弱网或断网立即进入离线缓存模式，不阻塞界面。
- 注入 `fetch` / `XMLHttpRequest` 缓存层，将成功响应写入本地缓存，断网时由缓存兜底。
- 页面顶部显示离线提示条，点击即可重连；网络恢复后自动重新加载在线页面，无需重启应用。
- 页面长时间无响应时展示重试界面并提供下拉刷新。

### 移动端能力补齐

- 通讯录、教务查询中的电话号码可直接拉起系统拨号盘。
- 权限管理可跳转到系统应用详情页，便于手动授予权限。
- 支持文件下载、系统文件预览、扫码、摇一摇打开校园码。
- 兼容 zfsoft 门户与通讯录 H5 的 Android 桥，补充二级页面、分享、版本检测等能力。

### 课表桌面卡片

- 三种尺寸：1×2 只看「此刻」，2×2 看今天剩余课程，2×4 带时间地点与剩余节数。
- 数据来自门户首页课表，加载完成后静默抓取落盘，断网时卡片仍可显示最后一次结果。
- 点击卡片直接回到 App 的主页。
- 配套的「上课提醒」在未来三天按课表提前 10 分钟提醒，重新抓取课表时自动重排。

### 隐私友好

- 首次启动展示系统半模态隐私声明，用户同意后才进入应用。
- 不接入统计、广告或第三方 SDK，不上传任何业务数据。
- 所有账号、密码与缓存均保存在设备本地，可在设置中清除。

## 更新说明

### 0.2.30 — 2026-11-04

**问题**：杀完后台立马点「我的」，还能看到「推荐软件」和「退出登录」。

0.2.28 那版做得不够，两个原因：

1. **「推荐软件」根本没在名单里。** 那一版只认「退出登录」「APP分享」几个字，而这两个词是猜的。
   实际这个页里还有个「推荐软件」区块（推广别的 App），从来没被处理过。
2. **注入太晚。** 脚本挂在 `onPageEnd`，而且只扫 4 秒（10 轮 × 400ms）就收工。杀后台走的是缓存
   恢复，`onPageEnd` 可能很早就来过、也可能来得比按钮渲染还早；等你「立马点」进去时，
   扫描窗口已经关了，按钮这才慢悠悠地长出来 —— 自然看不见。

**改法**：

- **挪到 `javaScriptOnDocumentStart` 注入**（`WebTab` 里本来就在用它给门户塞桥脚本）。
  这是文档开始解析时就执行的点位，不受缓存恢复影响；`MutationObserver` 改成常驻不再停，
  节点一插进 DOM 的那一下就会被标记。`onPageEnd` 的注入保留，作为 SPA 内部导航的补扫。
- **两类目标分开处理**：
  - `row` —— 单独一行（退出登录这类按钮），往上找「这一行除了它没别的文案」的容器一并藏。
  - `block` —— 带内容的区块（推荐软件 = 标题 + 一串 App），判据正好相反：**标题的同级里
    还有带文字的兄弟**，说明它是区块标题，连标题带列表一起藏。只藏标题会留下一截孤零零的图标。
- **两道保险防止吞掉整页**：闸一是兄弟节点数 ≤ 8（超过说明这不是「标题 + 内容」，
  而是页面根容器把东西平铺在一起），闸二是容器内文案 ≤ 40 条。真判不出来时宁可只藏标题。
- **内置诊断**：第一次在 `/my` 页跑起来 1.5 秒后，把页面上「看着能点」的文字打到 console，
  `WebTab` 的 `onConsole` 会转到 hilog（tag `WebTabJS`）。以后学校换文案导致又露出来了，
  看这条 `[dsh-mine]` 日志就知道它现在叫什么，不用再猜一轮。

**自检抓到过一个真 bug**：重写脚本时漏掉了首次 `sweep()`。document-start 那次扫描通常是空转
（body 还没长出来），但缓存恢复、页面已渲染完才补注入的场景全靠它，漏了就等于白跑。
`.tools/test_hide_mine_js.mjs` 现在 18 项断言，包含「区块要整块藏」和「不许吞整页」两条关键用例。

> **真机验证：待补。** 设备离线。装上后：杀后台 → 立刻点「我的」，看这三样还在不在。
> 若还在，抓一下 hilog 里的 `[dsh-mine]` 那条日志发我，照着它改文案就行。
> 回退：`历史版本\我的商大-0.2.29-signed.hap`。

### 0.2.28 — 2026-11-04

**问题**：「我的」页底部的「退出登录」和「APP分享」，和设置页里的两处重复了。

先厘清这两个入口的来历 —— 它们**不是 ArkTS 画的**，是门户 H5 自己渲染的按钮，
原版 App 用的是同一个网页，所以原版必然也有。我们这边只接住了点击之后的事：

| 入口 | 网页点了以后 | 设置页里的对应项 |
|---|---|---|
| 退出登录 | 走桥 `exitLogin/logout` → `Session.confirmAndClear()` | 设置页底部红色按钮，**同一个函数** |
| APP分享 | `Router.openExternal(OFFICIAL_APK_URL)` | 「APP分享」二级页：官方版 + 社区版 |

也就是说网页那份退出登录和设置页那份**完全等价**，纯冗余；而网页那份分享更糟 ——
`OFFICIAL_APK_URL` 是 zfsoft 的**安卓 APK** 下载页，鸿蒙上下下来也装不上，属于误导。

**改法**：加一段注入脚本 `HIDE_MINE_EXTRA_JS`，在门户页面加载完后把这两个入口藏掉。

- **不认 id / class，只认文案**：学校改版换 class 很常见，换文案不常见。比对前去掉所有空白，
  兼容「APP 分享」「退出登陆」。识别「退出登录 / 退出登陆 / 退出 / APP分享 / 分享APP」。
- **连整行一起藏**：只隐藏文字会留下一条空行。脚本从文字元素往上爬，条件是「这一行里除了
  这几个按钮没有别的文案」，抓大了就退回来只藏文字本身。字体图标（`&#xe600;` 这类私有区字符）
  不算文案，否则 `&lt;i class="icon"&gt;&lt;/i&gt;退出登录` 这种最常见的写法会爬不上去。
- **只在 `/my` 路径生效**，其它页面立刻 return。
- **最坏结果只是没生效**：整段包在 `try` 里，匹配不到就什么都不做，不会把页面弄坏。

配套自检 `.tools/test_hide_mine_js.mjs`：把脚本从 TS 里取出来，在迷你 DOM 上跑 11 项断言
（同卡两项、卡里有别项、带字体图标、非目标页、带空格文案、非 /my 路径），全过。

> **真机验证：待补。** 设备离线。这一版改的是「按文案匹配学校网页的 DOM」，
> 没上机之前不能确定文案对得上 —— 如果装上后这两个入口还在，说明学校用了别的写法，
> 需要抓一次页面结构再补文案（脚本本身不会报错，也不会影响页面）。
> 回退：`历史版本\我的商大-0.2.27-signed.hap`。

### 0.2.27 — 2026-11-04

**问题**：点首页那个「搜索应用、通知」的搜索框，页面会一层接一层地往右推，停不下来。

**成因**：首页那个「搜索应用、通知」是门户 H5 自己画的，点击后是网页内部导航到
`…/home/search`，触发 `WebTab` 的桥回调进来 —— `Router.openSub` 背后是
`NavPathStack.pushPathByName`，一个没有上限的栈。而同时还有第二条路在动：
`Index.onRouteEvent` 只要看到「非根 URL + 栈为空 + 不在处理中」，就会**再**开一个子页，
并且把当前 tab 重新 `loadUrl` 拉回根地址。于是出现闭环：

```
点搜索框 → 网页跳到非根地址 → onRouteEvent 压一层子页 → tab 被拉回根页（重新加载）
        → 页面加载完又把顶层地址改成非根 → onRouteEvent 再开子页 → …
```

两条路各自都能触发，彼此又互相喂，`stack.size()` 一路涨，用户看到的就是无限跳转。

**改法**：不猜哪一条是主因，两条都掐掉，再加一道硬闸。

- `common/Nav.ets` — `Router` 记住最近一次压栈的地址与时间：**同一地址 1.2 秒内再次请求直接丢弃**；
  另外 `stack.size() >= 6` 时不再压栈，给一句「页面层级太深，请返回后再试」。
  时间戳挡不住「A 开 B、B 又开 A」这种交替循环，层数总能挡住。
- `pages/Index.ets` — `onRouteEvent` 那条自动开子页的路，**同一地址 5 秒内只开一次**。
  这一条针对的正是上面那个「开子页 → 拉回根页 → 又跳过去」的自循环。

> **真机验证：待补。** 设备离线，这是连续第五个未装机验证的版本。
> 装包后重点看两件事：① 点首页搜索框只进一次搜索页，返回后停在该停在的地方；
> ② 正常点链接进子页、返回、再点同一个链接，不能被误挡（这是这两道去重最大的副作用风险）。
> 若行为异常，`历史版本\我的商大-0.2.26-signed.hap` 可直接回退。

### 0.2.26 — 2026-11-04

**问题**：0.2.25 给登录页开了自动填充，但用户改了密码后，密码保险箱里的旧密码并不会更新，
反过来还会把旧密码填进登录框。查官方文档得到两条关键信息：

> 页面跳转时触发保存功能……密码保险箱中已存在同应用下相同账号时，则弹出**密码更新**提示框。
> （FAQ）问：登录成功后并未触发密码保险箱特性，是否必须使用 router？**答：当前没有主动触发保存的方案。**

也就是说保险箱**不是主动比对**，它只在页面跳转那一刻去读用户名、密码两个输入框。
而我们的登录成功是同一个页面里把登录界面换成主界面（`needGate = false`），一次跳转都没有 ——
系统根本没等到那个时机，于是既不保存也不更新。

**改法**：把原本的 `struct Index` 抽成 `export struct MainShell`，新增 `pages/Main` 与
`pages/Index` 两个路由页面，二者都只渲染 `MainShell`。登录成功后 `navigateAfterLogin()`
在两者之间 `router.replaceUrl` —— 界面完全一样、用户无感、栈深度仍是 1，但系统看见了一次真实跳转。
之所以来回换而不是固定跳一个，是因为同 URL 的 `replaceUrl` 不一定被算作跳转。

配套：

- 换页失败（`replaceUrl` 抛错或 1.5 秒没走）时退回原来的原地切换，绝不把人卡在登录页。
- `aboutToDisappear` 补 `sensor.off(ACCELEROMETER)`。换页会销毁旧实例，监听不摘会一次摇动触发两遍。
- `main_pages.json` 增加 `pages/Main`。

> **真机验证：待补。** 这是本轮唯一改到页面结构的版本，出包时设备离线未能装机。
> 装包后重点看三件事：① 登录成功后能正常进主页（不会白屏/卡住）；
> ② 登录成功时系统弹出「保存密码 / 更新密码」；③ 杀后台再进仍能自动登录。
> 若出现异常，`历史版本\我的商大-0.2.25-signed.hap` 可直接回退。

### 0.2.25 — 2026-11-04

**一、冷启动与重新登录都固定落在主页。** 0.2.19 加的「恢复上次停留的 tab」去掉了 —— 实际用起来
很割裂：杀后台再进来，人还停在「我的」或「通讯录」，标题栏和内容都不是自己刚点出来的那一下，
像是应用没退干净。现在 `aboutToAppear` 直接把 `currentTab` 置为 `HOME_TAB`，
`PrefsStore` 的 `saveLastTab` / `getLastTab` / `KEY_LAST_TAB` 一并删掉（旧版本留下的那个键不再有用，
留着也无害）。

**二、登录页接入系统密码保险箱。** 登录页的两个输入框打开自动填充：
`.enableAutoFill(true)` + `.contentType(ContentType.USER_NAME / PASSWORD)`。
登录提交后系统会问「是否保存到密码保险箱」，下次进登录页会自动把账号密码填回来。
眼睛图标只是把内容显示成明文，`contentType` 仍是 `PASSWORD`，保险箱照样认得。

> 为什么只开这一处：0.2.21 曾把主 Web 的自动填充关掉，因为自动登录每次冷启动都会替用户
> 提交一次带密码的表单，系统把它当成用户主动登录，于是每次进来都弹「是否更新密码」。
> 那是噪音，该关；登录页这个是人手动输、手动点的地方，该开。**主 Web 与校验用的隐藏 Web
> 继续保持 `enableAutoFill(false)`。**

两者分工：我们自己存的凭据（Asset Store）负责「静默自动登录，用户连登录页都看不到」；
系统保险箱是另一层保险 —— 万一我们的存储不可用，账号密码还能被填回来。

### 0.2.24 — 2026-11-04

真机测出来的结论很直白：勾上「记住密码」登录，提示「本机加密不可用，密码未保存」——
也就是说 **存这一步从来没成功过**。0.2.23 里那把「删掉密钥重建再试」的重试也没救回来。

回头看，0.2.21 及更早之所以「记得住」，是因为校验失败时会退回 preferences 存一份明文；
0.2.22 掐掉明文兜底之后，这个功能就整体消失了。问题不在兜底，在于加密本身就没通。

**一、账号密码改存系统的资产存储（Asset Store Kit）。** 新建 `common/CredStore.ets`，
用 `asset.add` / `asset.query` / `asset.remove` 存取一条别名资产，内容是
`{"user":"...","pass":"..."}` 的 UTF-8 字节，`ACCESSIBILITY` 取 `DEVICE_FIRST_UNLOCKED`
（设备首次解锁后可读，不同步、不上云）。密钥由系统托管，应用只拿到别名，不需要也无法导出密钥材料。

存取顺序变成：**资产存储 → 自己拼的 HUKS（保留作回退）→ 都不通就不存**。绝不写明文。
`clearLogin` 两处都清，否则「退出登录」会变成假的；`migrateLegacy` 也改成把遗留明文迁进资产存储，
迁完回读校验通过才删明文。

**二、冷启动把凭据同时放进 AppStorage。** 各 tab 的自动登录先读自己那份（`aboutToAppear` 里异步读盘），
读不到才看 `dsh_session_pass`。冷启动时页面有可能比读盘先加载完，缺这条兜底就会「明明记住了密码，
却提示未登录」。

**三、其余沿用 0.2.23**：登录失败按现场给原因（验证码 / 学校原话 / 没提交上去 / 空密码）、
提交前重新断言输入框、不再因子页面被弹回就删凭据。

> **验证要点**：登录成功时提示「登录成功，已记住账号密码」才算存下；
> 杀后台再进应直接进主页。若仍提示「密码未保存」，说明这台设备的资产存储也不可用，
> 看 `hilog -T CredStore` 里的 `asset add failed`。

### 0.2.23 — 2026-11-04

全部围绕登录这条路。起因是 0.2.22 之后冒出两个现象：同一组账号密码第一次能登、第二次却说密码错；
以及登录成功、杀掉后台再进来又要重新登录。

**一、记住密码可能根本没存下。** 凭据是 HUKS 加密后存的，写之前会解一次做往返校验。校验不通过时，
0.2.22 的做法是**直接不存** —— 安全上没错，但界面上只有一句 2.6 秒的提示，用户很容易错过，
结果就是「记住密码」静默失效。

现在改成：往返校验不通时，先 `deleteKeyItem` 把旧密钥删掉重建一把再试一次（多半是早期版本留下的
密钥跟现在的 `initSession` 参数对不上），还不行才放弃。丢掉一把解不开的密钥没有损失 —— 它对应的
密文本来也解不回来。

**二、不再因为「某个页面被弹回登录页」就删掉记住的密码。** 以前自动登录连续两轮被送回登录页，
就判定「账号或密码错误」，同时 `clearLogin` 删凭据、把人踹回登录页。但「被弹回」不等于密码错：
通讯录这类子服务有自己的 SSO 入口，它不兼容时也会被弹回，而代价是用户从此失去记住密码。

现在只有**门户首页**（`isPortalUrl(rootUrl) && scrapeSchedule`）反复失败才认定凭据失效，
阈值从 2 提到 3，并且任何情况下都不再删已保存的凭据 —— 真错了也没关系，用户重新登录一次就覆盖了。

**三、登录失败会说清原因。** 以前只要提交后被送回登录页，一律报「账号或密码错误」。但同一个 URL
底下可能是三件事：密码真错、学校要求输验证码、表单压根没提交上去。新增 `PROBE_STATE_JS` 读回
页面现场（`#errormsg` / `#msg` / 验证码是否可见 / 脚本走到哪一步 / 两个输入框还剩几个字符），
按实际情况给文案：

| 现场 | 提示 |
| --- | --- |
| 验证码可见 | 学校这次要求输入验证码：请先用手机浏览器打开统一身份认证登录一次，再回来重试 |
| 页面有错误文案 | 学校提示：<原话> |
| 该提交却没提交（`blocked`） | 登录页没准备好（没拿到加密公钥），请稍后重试 |
| 提交了但没回应 | 提交后学校没有回应，请检查网络后重试 |
| 密码框是空的 | 密码没能填进登录框，请重试 |
| 以上都不是 | 账号或密码错误，请重新输入 |

**四、提交前重新断言输入值。** 学校登录页在 ready 里有一句 `$("#ppassword").val($("#password").val())`，
`#password` 是隐藏域、新页面里是空的。只要它比我们的填充晚一步执行，刚填进去的密码就被清成空串，
提交上去等于空密码，服务器必然打回 —— 这正是「刚才还能登、这次说密码错」的机制。现在 `submit()`
每轮点击前都比对一次，不一致就重填。

**五、日志。** `saveLogin` 每个分支都写一行，`getLogin` 在「有密文却解不回来」时也写 ——
这是「记住密码突然失效」唯一能对得上号的线索。

### 0.2.22 — 2026-11-03

这一版没有新功能，全部是之前记在待办上的欠账：五处真缺陷、三处工程债。同时把版本号往上抬一格 ——
从这一版起一个功能批次升一次，覆盖安装才不会被判降级（`versionCode` 不递增会报 downgrade，
只能靠 `hdc install -d` 强降），出问题也能按版本回溯。

**一、凭据加密的 nonce 换了随机源。** 原来用 `Math.random()` 生成 12 字节的 GCM nonce。
它是伪随机，且同一次启动内的序列可预测；而 GCM 一旦 nonce 重复，两条密文的异或就直接泄露明文关系，
严重的能恢复出明文 —— 加密等于白做。改用 `cryptoFramework.createRandom().generateRandomSync(12)`。
顺带把 `encrypt` / `decrypt` 各自包了 try/catch 并写日志，失败不再无声无息地返回空串。

**二、加密不可用时不再退回明文存密码。** 原来 HUKS 不可用会在 `preferences` 里明文存一份，
理由是「保证记住密码这个功能不失效」。这个取舍是错的：`preferences` 是沙箱里的普通文件，能被备份、
能被三方工具读到，而这里存的是统一身份认证的密码 —— 泄露一次，教务、邮箱、一卡通跟着全失守。

- `saveLogin` 改为返回「是否真的存下了」。存不下就把四个键全清掉，一个字节的凭据都不留。
- 登录成功的提示跟着分叉：「登录成功，已记住账号密码」/「登录成功，本机加密不可用，密码未保存」
  （后者停 2.6 秒，够看清），不再一律说「已记住」。
- 老版本留下的明文凭据改走新加的 `migrateLegacy()`：能加密才迁移、往返校验通过才落盘、
  迁不动就原样留着先保住自动登录。**不能**复用 `saveLogin` —— 那条路在加密失败时会把四个键全删，
  等于在这次启动里把用户唯一的一份凭据抹了。

**三、网页要权限，只给学校自己的域名。** `onPermissionRequest` 原来是无条件
`grant(getAccessibleResource())`：页面一旦被导航到第三方站点，那边张口要摄像头、麦克风、定位，
也是一句话就拿到，用户完全不会被告知。现在按来源判断 —— 新增的 `isSchoolUrl()` 只看主机名是否为
`zjgsu.edu.cn` 或其子域（去端口后精确比较，`https://zjgsu.evil.com`、`https://evil.com/#zjgsu.edu.cn`
这类子串伎俩过不了），是才授予，否则 `deny()` 并记日志。注意 `OnPermissionRequestEvent` 本身只有
`request` 一个字段，来源得从 `request.getOrigin()` 取，`event.origin` 不存在。

**四、学校网页关掉 `file://` 访问。** `.fileAccess(true)` 原来是写死的，等于给每个加载的网页开了
读本地文件的通道，而门户根本用不到。改成 `.fileAccess(!isHttpUrl(this.rootUrl))`：只有本地 `rawfile`
页面（首次启动的隐私声明、加载失败页）需要这一项，http/https 一律关。

**五、协议勾选不再替用户预勾。** 退出登录回到登录页时 `agreeTerms` 被设成 `true`，
「我已阅读并同意《用户协议》」已经是勾好的状态，用户点一下登录就等于默认同意。这类同意必须由用户
主动做出，改成 `false`。

**六、作息表收归一处。** `PERIOD_START` 之前在三处各写一份（`Reminders.ets`、`ScheduleCardAbility.ets`、
以及解析侧隐含的节次数），改一处忘一处就会出现「提醒时间和卡片显示对不上」。现在统一到
`common/Periods.ets`：起止时间表 + `toMinutes()` / `startOf()` / `endOf()`，其余文件只 import。

**七、学期与周次真正用上。** 抓课表时 `term` 和 `week` 一直在解析、一直在落盘，界面上却从没出现过，
等于白抓。设置页「上课提醒」下面新增「当前学期」一行，显示周次简称（如「第八周」），点一下 toast

  换账号后会出现数据串号：「我的」页仍是上一个人的姓名、学号、成绩、一卡通余额（来自 localStorage 里
  `__dsh_http_cache_v1__` 的接口响应缓存），桌面卡片仍是上一个人的课表，待办通知和角标还挂着，
  已排的上课提醒还按上一个人的课表响。

  现在拆成两档：

  - `clearAll()`：用户主动退出，全清 —— Cookie、`WebStorage.deleteAllData()`
    （localStorage / Web SQL / IndexedDB）、`basic.json` / `todo.json` / `schedule.json`、
    凭据、待办通知与桌面角标、`Reminders.cancelAll()`、AppStorage 状态。
  - `clearSession()`：只是会话失效（票据过期、密码输错），只清 Cookie 和凭据，离线课表与已排提醒留着，
    重新登录后卡片立刻有内容，不用再等一次抓取。

  `Index.onLoginFailed()` 改用 `clearSession()`，避免每次会话过期都把课表缓存和提醒一起清掉。
  另外 `dsh_logout_ts` 用 `now > old ? now : old + 1` 兜底（同一毫秒内两次登出也能触发 `@Watch`），
  `dsh_last_todo` 归零（否则下次抓到的条数比它小就不再推通知、不再亮角标）。

  真机验证：点「退出登录」后 `files/` 变空、prefs 里账号密码消失、界面回到登录页；
  重新登录后 `schedule.json` / `todo.json` 重新生成、凭据重新写入、冷启动自动登录正常。

  **三、提醒的三处加固，以及「到点不响」的真机结论（提交 `b939f7c`）**

  加固（都是为了少踩坑，与下面的设备问题无关）：

  - 清空提醒改用 `cancelAllReminders()`。原来只走「`getValidReminders()` 拿列表 → 逐条
    `cancelReminder`」，列表接口在个别设备上会抛错（日志 `ReminderAgentService: Read result failed,
    code is: 1`），一抛整批都删不掉，紧接着的 `publish` 就撞上限。逐条删保留作兜底。
  - `aliveCount()` 出错返回 `-1` 而不是 `0`。以前静默返回 0，读不到就当「一条都没有」，
    于是每次进 App 都判定要重建：清不掉旧的、再发一批新的、撞上限、后半批全失败。
  - 提醒请求显式指定 `slotType: SOCIAL_COMMUNICATION`，发布前调一次 `addSlot()`（幂等）；
    `requestEnableNotification` 的成功/失败都写日志并带上错误码。

  真机结论：**这台设备上提醒发布不出去，且不是代码问题**。日志两侧对照如下——

  ```
  应用侧：sync: courses=17 expect=17 alive=0 → cancelAllReminders ok → slot ready
          → notification granted → republish 17 of 17 → publish failed（17 次）
  系统侧：ReminderControl com.humour.myshangda, notification not allowed.
          ANS_REMINDER: The number of reminders exceeds the limit[0].
  ```

  那个 `limit[0]` 是关键：不是 30 条上限打满，而是系统把该应用的提醒配额算成了 **0 条**，起因是
  `notification not allowed`。而同一时刻：系统设置里「允许通知」是开着的、`isNotificationEnabled()`、
  `requestEnableNotification()`、`addSlot()` 全部返回成功 —— 三方状态互相矛盾，属系统侧记录异常。
  卸载重装、在授权弹窗点「允许」、把设置里的开关关掉再打开，都试过，仍判否。
  换设备或重置系统通知状态后应可恢复。`bm dump` 里的 `allowEnableNotification` 字段与真实状态无关
  （重装前后、点允许/不允许之后都是 `false`），不要拿它判断。

## 构建与运行

环境要求：

- DevEco Studio 6.1 及以上
- HarmonyOS SDK 6.1.1（API 24）及以上，目标 API 26
- 一台 HarmonyOS 真机或模拟器

命令行构建：

```bash
hvigorw assembleHap --mode module -p product=default -p buildMode=release --no-daemon
```

产物位于：

```text
entry/build/default/outputs/default/entry-default-signed.hap
```

仓库不包含任何签名证书。首次打开工程时，请在 DevEco Studio 中进入 **File → Project Structure → Signing Configs**，勾选自动签名或配置自己的证书。

安装与启动：

```bash
hdc install -r entry/build/default/outputs/default/entry-default-signed.hap
hdc shell aa start -a EntryAbility -b com.humour.myshangda
```

## 使用说明

1. 首次启动阅读并同意隐私声明。
2. 在登录页输入学校统一身份认证的学号 / 工号与密码，可选择记住密码。
3. 登录成功后进入主页，底部导航可切换消息、审批、主页、通讯录、我的。
4. 设置页可切换界面样式、清理缓存或退出登录。
